## Description

Ramener les 4 gates de `packages/dcm-frontend` à un exit 0 : `lint` → `typecheck` → `tests` →
`build`. Ce n'est pas une dette découverte par T003 mais **l'état de `develop`** : les mêmes
compteurs sortent à l'identique avec et sans les fichiers de T003.

Cette task existe parce que le gate de commit du workflow DCM lit ces 4 gates
(`dcm-review.sh` + `review.before_commit_require_pass: true` dans `dcm-config.yml`) : tant
qu'ils sortent non-zéro, **aucun** commit du package ne peut obtenir de stamp de review, quelle
que soit la qualité du diff proposé. Le coût est donc payé une fois ici, au lieu d'être contourné
à chaque commit.

**Aucun changement fonctionnel.** Pas de nouvelle fonctionnalité, pas de refonte de page, pas de
renommage de route ni de libellé d'IHM. Les seules modifications de comportement autorisées sont
celles qu'exige la correction d'un des 4 tests rouges — et elles se justifient une par une dans la
PR.

## Ordre de traitement (du risque nul au risque réel)

Découpage voulu pour rester en petites PR, chacune vérifiable seule :

1. **Code mort** — supprimer les imports, variables, paramètres et types déclarés et jamais lus.
   Ferme les **39** erreurs eslint et **30** erreurs `tsc` (`TS6133` + `TS6196`) d'un seul
   mouvement, sans aucun changement de comportement. Ne pas « utiliser » une variable pour taire
   la règle ; ne pas la préfixer d'un `_` si elle est simplement à supprimer.
2. **Typage des paramètres de requête** — `api/dcmApiClient.ts` et les hooks `use*PageData.ts`
   (`TS2345`, `TS2411`, `TS2322`, `TS2739`). Corriger la **forme du type**, pas le symptôme :
   aucun `as any`, aucun `@ts-expect-error` sans commentaire justifiant pourquoi le type ne peut
   pas être juste.
3. **Les 4 tests rouges** — dans l'ordre du tableau ci-dessus. Pour le `.length` sur `undefined`,
   décider explicitement dans la PR : garde dans le composant (bug de prod) ou fixture complétée
   (défaut de test).
4. **`react-hooks/exhaustive-deps` (16 warnings)** — un par un, en dernier parce que c'est le seul
   lot qui peut **changer le comportement au runtime** : ajouter une dépendance manquante peut
   déclencher une boucle de refetch. Soit la dépendance est ajoutée et le rendu vérifié, soit le
   warning est désactivé ligne à ligne avec un commentaire disant pourquoi l'omission est
   volontaire. Pas de désactivation globale dans `eslint.config.js`.
5. **`react-refresh/only-export-components` (6 warnings)** — déplacer l'export non-composant dans
   un module voisin, ou désactiver la règle sur la ligne avec sa raison.

## Tests

Les gates sont eux-mêmes le test. Les deux commandes qui donnent la liste à jour :

```bash
cd packages/dcm-frontend
npx eslint src --ext ts,tsx --report-unused-disable-directives --max-warnings 0
npx tsc --noEmit
npx vitest run
npm run build
```

Vérification de non-régression à chaque étape du découpage : le compteur doit **descendre**
strictement et le nombre de tests verts ne jamais baisser.
