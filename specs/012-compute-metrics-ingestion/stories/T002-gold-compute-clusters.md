## Description

Create the new `pipelines/gold_dbx_compute/` plugin (scaffolding + cluster metrics) computing 4 daily/snapshot gold tables from curated data: `gold_dbx_compute_cluster_cost_daily`, `gold_dbx_compute_cluster_efficiency_daily`, `gold_dbx_compute_cluster_reliability_daily`, `gold_dbx_compute_cluster_governance` (FR-004 to FR-007). This task **creates the shared scaffolding** (`__init__.py`, `specs.py` registry, `entrypoint.py`, `resources/job_dcm_gold_dbx_compute.yml`) that T003 and T004 will extend — see `merge-strategy.md` for the resulting shared-file conflict rules.

- CREATE `packages/dcm-databricks-pipeline/pipelines/gold_dbx_compute/specs.py` — registry of gold aggregation specs (source curated table(s) → target gold table, grain, merge keys).   - `gold_dbx_compute_cluster_reliability_daily`: start count, avg startup seconds, unexpected terminations, auto-termination config.
  - `gold_dbx_compute_cluster_governance`: snapshot (no `period_start`) of tag/DBR/oversize compliance + `recommended_action`/`severity` priority rule (tag manquant > DBR obsolète > oversize).

### Deviations & known limitations (T002 implementation)

- **Job orchestration : taches explicites chainees par `depends_on`, PAS de `for_each_task`.** `cluster_efficiency_daily` lit `gold_dbx_compute_cluster_cost_daily` (pour `estimated_savings_usd`) et `cluster_governance` lit `gold_dbx_compute_cluster_efficiency_daily` (pour `node_oversized`) : un `for_each_task` parallele (comme `job_dcm_system_tables.yml`, tables independantes) introduirait une course (lecture d'une table gold pas encore a jour). `job_dcm_gold_dbx_compute.yml` declare donc 4 taches explicites : `gold_cluster_cost_daily` -> `gold_cluster_efficiency_daily` -> `gold_cluster_governance` (chaine), `gold_cluster_reliability_daily` en parallele (independante). Le registre `GOLD_SPECS`/dispatch `entrypoint.py` restent neanmoins generiques (dict par cle) pour T003/T004.
- **`curated_dbx_access_audit` (T001) ne contient pas encore les evenements de cycle de vie cluster.** Le filtre actuel (`ACCESS_AUDIT_ROW_FILTER` dans `system_tables/specs.py`, proprietaire T001) ne retient que `getTable`/`createTable`/`deleteTable`. La logique de `gold_dbx_compute_cluster_reliability_daily` (start_count, avg_startup_seconds, unexpected_termination_count, top_termination_reason) est ecrite et testee (texte SQL) mais produira 0/NULL en production tant que ce filtre n'est pas elargi — a signaler au owner de `system_tables` (hors scope T002, fichier proprietaire different par merge-strategy.md).
- **`curated_dbx_compute_node_types` n'a pas de colonne de prix.** `recommended_node_type`/`estimated_savings_usd` (efficiency_daily) approximent via un ratio de `core_count` (node plus petit le plus proche) au lieu d'un vrai cout par node_type (donnee absente du referentiel systeme). A ameliorer si un mapping node_type -> SKU/prix devient disponible.
- **Jointure `dim_landing_zone` :** assumee sur `dlz.subscription_or_account_id = <table>.account_id AND dlz.cloud_provider = <table>.cloud_provider AND dlz.is_current = true`, colonnes alignees sur `docs/02-data-model/data-models.md` (dimension SCD2 existante). A confirmer avec le owner de cette table de reference si le nom/schema differe en prod.
- **Refinement post-review : `governance.dbr_is_lts_current` derive desormais d'une fenetre de support calculee, pas d'une liste figee.** `specs.py` remplace `DBR_LTS_SUPPORTED_VERSIONS` (frozenset statique, a purger manuellement a chaque fin de support) par `DBR_LTS_RELEASE_DATES` (date GA par version, on ne fait qu'ajouter une ligne a chaque nouvelle LTS) + `DBR_LTS_SUPPORT_WINDOW_YEARS = 3` (duree de support LTS Databricks documentee). `cluster_metrics.dbr_lts_versions_supported_as_of(today, ...)` calcule l'ensemble des versions encore supportees a la date du run (`today` threade depuis `entrypoint.main()`, jamais `date.today()` inline — reste testable). Couvert par 2 tests supplementaires (`test_dbr_lts_versions_supported_as_of_keeps_versions_within_support_window`, `test_dbr_lts_versions_supported_as_of_drops_expired_versions`).
- **Refinement post-review : retrait de `source_lz_id`/`ba_name` des 4 tables gold clusters.** Le join vers `dim_landing_zone` comparait `account_id` (UUID du compte Databricks, issu de `system.billing.usage`/`system.compute.clusters`) avec `dim_landing_zone.subscription_or_account_id` (identifiant cloud AWS/Azure natif) : deux espaces d'identifiants distincts, join qui ne matchait jamais (`source_lz_id`/`ba_name` toujours NULL en pratique). Aucun mapping `workspace_id → lz_id` fiable n'existe aujourd'hui dans le repo (verifie : ni system tables, ni curated de l'ancien pipeline collecteur qui ne couvre que 3 workspaces sur 597). **Decision** : retirer `source_lz_id`/`ba_name` plutot que d'exposer une dimension toujours NULL. Nouveau grain : `(cloud_provider, workspace_id, cluster_id, period_start)` pour les 3 `*_daily`, `(cloud_provider, workspace_id, cluster_id)` pour `governance`. `cost_rank`/`is_top_cost` passent d'un classement par LZ a un classement **global par jour** (`PARTITION BY period_start`). Impact : `specs.py` (`CLUSTER_DAILY_MERGE_KEYS`/`CLUSTER_GOVERNANCE_MERGE_KEYS`, `source_tables` des 4 specs, suppression de `DIM_LANDING_ZONE`), `cluster_metrics.py` (suppression du parametre `dim_landing_zone_table` et des joins associes dans les 4 fonctions, jointures `clusters_table` pour les autres colonnes preservees), `entrypoint.py` (suppression de `dim_landing_zone_table=...` dans les 4 appels de builders). Documents transverses mis a jour en consequence : `data-model.md`, `spec.md` (US2 scenario 1, FR-004), `contracts/gold-tables-contract.md` (exception documentee sur les colonnes obligatoires), `research.md` (R8). ### Fix ciblé (4e round) : priorite `owner` dans `gold_dbx_compute_cluster_cost_daily` — le tag explicite doit gagner sur `owned_by`
